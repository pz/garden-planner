# `src/solver/` — the planting solver

Turns a `PlantingSpec` plus a `GardenPlan` into a batch of API commands (`solve`), and a harness
to run it against fixture gardens. It is the engine behind the planned planting assistant, but has
no LLM in it. It sits between `src/api` and `src/app`: it may import `types`, `data`, `core` and
`api`; nothing in those layers may import it, and it must not import `app` (enforced in
`.oxlintrc.json`; `tsconfig.core.json` typechecks it without the DOM lib).

The design is the [Planting Solver & Test Harness — Design](https://claude.ai/artifact/9Peko4zYhPUAfoHUMdjPmt) doc. This README records what has
been built and every decision made while building it that the doc left open or changed.

## Layout

- `spec.ts`: `PlantingSpec` and `parseSpec(raw, plan)`; the defaults (`DEFAULT_FILL_RATIO`, `DEFAULT_PREFS`).
- `scenario.ts`: the scenario file type and `parseScenario`.
- `catalog.ts`: the fixture registry plus `loadGarden` and `loadScenario`.
- `fixtures/{gardens,specs,scenarios}/`: plain JSON. A garden is the app's Export file, so a garden made in the app can be dropped in.
- `session.ts`: what the solver viewer does around `solve` (parse a typed spec and solve, which plants are new, score-trace points).
- `cli.node.ts`: `npm run solve -- --list | <scenario> | --all`.

## Decisions

Numbered so later milestones can refer to them.

1. **Integration branch.** Work happens on `planting-solver`; each milestone is a PR on its own branch (`solver-m<N>-…`) stacked on the previous one, and the stack is merged into `planting-solver` before it goes to `main`.
2. **Spec shape.** The doc's type block didn't survive, so the shape is ours: `{ mode, demands, scope?: { bedIds? }, locked?, exclude?, fillRatio?, prefs? }`. The scope is an object so it can grow (for example per-bed rules) without a breaking change.
3. **Spec validation.** `parseSpec` reports every error with a JSON pointer, in the API's `ApiError` shape. `invalid_command` is a bad shape or value, `unknown_crop` / `unknown_bed` an id that matches nothing, `unknown_id` a locked groupId that matches no patch. Beyond the doc: an empty `bedIds` list is an error (it would otherwise be read as "nowhere"), a crop demanded twice is an error, and a crop both demanded and excluded is an error. A demand's `bedIds` must lie inside the scope.
4. **Defaults.** `fillRatio` 0.85. Preferences run 0 to 1, defaulting to spacing 1, shade 1, companions 1, clustering 0.3, stability 0.5. All are first guesses, to be tuned with the sweep in milestone 4. `parseSpec` returns the spec as given; applying defaults is the solver's job.
5. **Scenario files are strict.** An unknown expectation kind or field fails the load, so a typo can't silently remove a check. Expectation names are as in the doc, with `warningKind` as the field that names the warning kind (the bare word `kind` is the expectation's own).
6. **Fixtures are imported by name, not globbed.** `catalog.ts` imports each JSON file explicitly. That works the same in Node, tsx, vitest and the app, and typechecks under `tsconfig.core.json` (no Vite types). `catalog.node.test.ts` fails if a file in `fixtures/` isn't registered. The viewer can switch to `import.meta.glob` later if it wants to.
7. **Node-only files.** Files named `*.node.ts` or `*.node.test.ts` may use Node APIs. `tsconfig.core.json` and `tsconfig.app.json` exclude them and `tsconfig.node.json` checks them. To let that config import the JSON fixtures, it now uses `module: esnext` with bundler resolution (it only covered the Vite/Vitest config files before).
8. **Garden fixtures.** The doc's "48×96 bed" is the app's default bed, which is 96 wide by 48 tall, so that is what `empty-4x8` uses. Three gardens beyond the six in the doc, which specs need: `north-row-east` (the doc's "northDeg 90 variant"), `short-season` (zone 3) and `custom-crop` (carries a user-made crop in the file's `customCrops`). Fixtures with a location use latitude 40 so the shade direction is defined.
9. **Custom crops are process-wide state.** `loadGarden` registers the garden file's custom crops with `data/crops` (replacing earlier ones), because `findCrop` reads from there. Specs are therefore validated after their garden loads. "Has no schedule" in the solver means `hasSchedule(crop) === false`, which already exists.
10. **Scenario expectations are provisional.** Milestone 1 only checks that scenarios load and validate. The expectations were written from the doc, before a solver exists, and may be tightened or corrected in milestones 3 to 5 when they first run.
11. **PRNG.** `mulberry32` moved to `src/core/random.ts` with tests (including a pinned value), and `api/simulation.test.ts` imports it.
12. **`HARD_SPACING_FACTOR`** already exists in `core/spacing.ts` (0.7); the solver will import it rather than define a second copy.
13. **Blocks are always axis `x`.** A `columns × rows` block on axis `y` is the same points as a `rows × columns` block on axis `x`, and the search tries every shape, so searching both axes would only duplicate candidates. `asBlock` also normalizes to `x`. The field stays in the type so a block round-trips to an `addPatch` grid.
14. **Rules mirror core exactly.** `rules.ts` uses the same distance formula (`sqrt(dx²+dy²)`), the same average-of-spacings gap and the same strict comparisons as `core/spacing.ts` and `api/warnings.ts`, so the solver and the warnings cannot disagree by a rounding error. The one deliberate difference: the hard limit is `HARD_SLACK_IN` (1e-9 in) conservative, so a placement exactly on the 0.7 line is refused rather than left to floating point.
15. **Grid tolerance.** `asBlock` accepts coordinates within 0.01 in of a grid line (what the UI's rounding can produce) and nothing looser. A patch that fails is fixed, never reshaped.
16. **Edge spill samples** are written out as eight exact offsets rather than computed with `cos`/`sin`, so a plant flush with a straight wall does not count the sample along the wall as outside (`cos(π/2)` is not exactly 0).
17. **Fixed plants never count toward a demand.** `placed`, a demand's `min`/`max` and the demand curve all count only plants the solver places or keeps (blocks). In adjust mode a demand means "the desired total", and the existing patches of that crop are blocks, so they are included; locked or non-grid patches are fixed and are not. This settles the doc's open question about whether the free area `A` and the count `n` use the same base.
18. **Allocation area is per crop.** A crop's `A` is the free area (bed area minus the growing rooms of fixed plants) of the beds it may use. `Σw` is over every demand that survived the filters. A crop asked for always gets a target of at least 1; whether even one fits is for the search to find out.
19. **Candidate blocks.** From each lattice anchor, for each width, the tallest block that satisfies the hard constraints, cut to land on the remaining count (rounded down, or up if that overshoots by at most one plant). Feasibility only shrinks as a block grows, so trying the tallest is enough. Candidates are tried best demand-gain first and the search stops when no remaining one can beat the best found, since every penalty only lowers a score.
20. **Greedy tie-breaks.** The doc says seeded random. Equal scores prefer the block nearest the bed's top-left corner (then the earlier bed), which packs far better, and only exact remaining ties use the seeded random choice. Annealing (milestone 4) supplies the diversity.
21. **A block must gain more than `MIN_GAIN` (1e-9) to be added.** So the greedy pass never adds a block whose crowding or spill costs more than it earns, even below the target.
22. **No `iterations`/timing in the greedy result yet, and no clock in `solve`.** Timing is measured by the CLI, so `solve` stays deterministic. The season check takes `options.year` (default: this year); tests and the CLI pass 2026.
23. **Season fixture.** In the zone table, a watermelon (transplant 1 week after the last frost, 80 days) still ripens in zone 3 (Aug 25 against a Sep 1 frost), so `fill-short-season` uses an artichoke (150 days) for the "too short" case and keeps the watermelon as a control.
24. **A tiny bed is not "no room" (superseded by 43: with the default edge clearance it is).** The doc lets a plant's growing room spill past the bed edge as long as its center is inside, so a 24 in bed always takes one squash. `insufficient_space` therefore comes from fixed plants crowding a spot out (see `solve.test.ts`), and `fill-tiny-bed` now expects one squash, one tomato and radishes for the rest.
25. **Pending scenarios.** `scenarios.test.ts` lists the scenarios that need a later milestone (shade terms, adjust and replace) with `it.skip` and the reason; each milestone removes its entries.
26. **Pair terms are recomputed on removal.** A pair is counted when its later block is added, so removing the earlier block must also take out the pairs it has with blocks added since. `Evaluator.remove` therefore recomputes the group's contribution against what is left instead of replaying what it stored. `search.test.ts` checks the running totals against a fresh evaluator after random adds and removes, and `previewAdd` against `add`.
27. **Shade and companion rules are the core rules, vectorised by patch.** `pairRules.ts` repeats `findShadeConflicts` and `findCompanionConflicts` per pair of patches with a bounding-box prefilter, and `consistency.test.ts` checks both against core on 200 random gardens with turned beds and any north (including a southern latitude). Shade is charged per plant of the shaded patch; companion per pair, 1 for extension evidence and 0.5 for anecdotal.
28. **"Downstream" in the doc means where the shadow ends up.** Shadows fall toward north in the northern hemisphere, so tall crops belong on the north side of a bed or garden, where nothing lies ahead of them. `search.test.ts` checks that on `north-row` and `north-row-east` the tall corn ends up with no shade conflict at all, whichever way north points.
29. **Annealing.** Geometric cooling from `T_START` 0.05 to `T_END` 0.0005 (a plant is worth 0.02 to 0.15). Moves, with probabilities: translate 0.35, grow/shrink 0.2, swap 0.1, relocate to another bed 0.1, delete 0.1, add a block for an under-target crop 0.15. A move that breaks a hard constraint is undone before it counts. The best state seen is kept and restored at the end, so the result never scores below the greedy start.
30. **First-guess weights** (all in `scoring.ts`): spacing 0.05 per unit of pair penalty, shade 0.08 per shaded plant, companion 0.3 per pair, clustering 0.1 per extra block, spill 0.04 per plant, sun 0.02 per full-sun plant in part shade, change 2 (milestone 5), BIG 1000. A median over 20 seeds of the score with search beats greedy alone by 0.01 to 0.15 on 11 of 15 scenarios, and ties on the rest, where the greedy pass is already best (`npm run solve -- --sweep`). The doc says "beats greedy on every scenario"; a tie on a scenario the greedy pass already solves optimally cannot be beaten, so the tests require a strict win on the scenarios that leave room and "never worse" everywhere. They have not been tuned further yet.
31. **Capacity is physical.** For "would it fit alone" (the `outcompeted` / `limited_by_bed_restriction` / `insufficient_space` reasons) `results.ts` repeatedly takes the largest block that satisfies the hard constraints, ignoring every soft cost. Using the real objective made a crop look as if it had no room when the search had merely chosen not to plant its last plants. A full-sun crop that falls short in a part-shade garden gets `insufficient_sun` instead of `outcompeted`.
32. **Performance.** 3000 iterations on `two-raised-beds` take about 150 ms in Node (the target was 300 ms); the unit test allows 1.5 s so a slow CI machine does not make it flaky. The greedy pass on the four-bed `odd-shapes` takes about half a second, dominated by candidate enumeration over several hundred anchors per bed.
33. **Who is editable.** Anything outside the scope, or locked, is fixed in every mode. Fill leaves the rest fixed; replace removes it (whatever the crop); adjust removes patches of an excluded crop (grid-shaped or not), turns a grid-shaped patch of a demanded crop in a bed that demand allows into a block the search can move, resize or drop, and leaves every other patch fixed (a crop nobody asked about, a hand-placed non-grid patch, a patch in a bed its demand excludes, a crop dropped by the season or sun filter).
34. **The change term.** For each existing editable patch: 0 if a block with its groupId is unchanged, the patch's plant count if it was moved, resized or taken to another bed, and the same count if it was dropped; divided by the editable plants in all, times `prefs.stability` × `CHANGE_WEIGHT` (2). Plants removed by `exclude` or `replace` are not charged (they are not a choice). New blocks cost nothing.
35. **Command order and shape.** Removals first (replaced or excluded patches, dropped patches, and reshaped ones), then `movePatch` for patches that only slid within their bed (plant ids survive), then `addPatch` for new blocks and reshaped ones. A patch that is resized or moved to another bed becomes `removePatch` + `addPatch`, because the API has no resize or cross-bed move.
36. **Over-target planting.** The demand curve still pays 0.05 per extra plant past the target, so once the targets are met the search may keep growing a crop that has room (replace-bed-2 plants 16 basil against a target of 9 because the cucumbers cannot use the space). The `met` status stands; `placed` reports what was planted.
37. **Invariant: a patch outside the scope is never named in a command**, in addition to the doc's "fixed and locked plants are byte-identical".
38. **Viewer route is `/_solver` (or `#/_solver`)**, matching the sprite sheet's `/_sprites`, not the doc's `#/solver`, so one convention covers PR previews on hosts that 404 unknown paths.
39. **Compiled out like the mock API (superseded by 52: it now ships).** `App.tsx` imports the page with `import.meta.env.DEV ? lazy(() => import('./solver/SolverPage')) : null`; in a production build that is `false`, so the page, the solver and its fixtures are dropped (the bundle is byte-identical in size to before). CI's existing grep for the mock API now also greps for `solver-viewer`, the page's test id.
40. **Sources and apply.** A scenario's garden is held in an in-memory `GardenApi` (nothing is saved); "Current garden" uses the real stored garden. Either way "Apply to this garden" calls `apply(commands, { ifRev, scope: 'planting' })` through the same `GardenProvider` the app uses, so a stale revision or a refusal shows up exactly as it would for a real client. Fixtures are imported by name (decision 6), not with `import.meta.glob`, which still works here.
41. **Before and after use the app's sprite art** (`SpriteArt`) in each bed's own frame, read-only, with a dashed ring on plants the proposal adds. Beds are not drawn turned, since the solver plans in the bed's own frame.

### Layout quality (from the first round of real use)

Examples of bad outcomes were collected in the design doc's review and fixed together. Each of 42 to 48 answers one or more of them.

42. **A weight of 0 means ignore the crop.** `parseSpec` accepts 0 (negatives are still errors). A weight-0 crop gets no target and is never planted, its existing patches are left alone in adjust mode (it is not a demand, so they are not editable), and it still gets a `CropResult` (target 0, placed 0, `met`) so the "every demand has a result" invariant holds. If every weight is 0 nothing is planted and there is nothing to divide by.
43. **Edge clearance is relative to the plant, default 0.5.** A spec's `edgeClearance` is a fraction of a plant's growing-room radius (half its spacing): how far in from the bed edge its center must stay. 1 keeps the whole growing room inside the bed, the default 0.5 puts the center half a radius in so about a quarter of the plant overhangs (a tomato's center is 6 in from the edge, a radish's 0.5 in), 0 lets plants sit right on the edge, and up to 2 leaves a margin. It is a hard constraint, checked by `insideWithClearance` (exact for rectangles, rounded corners and polygons; an ellipse by a shrunk ellipse plus a ring of samples). The first version (default: the whole room inside, or an absolute number of inches) put plants too far in for small beds and was absolute for numbers; relative is the better unit because a tomato and a radish want different margins. The design doc's soft spill penalty remains for the overhang. Targets use the bed shrunk by any clearance beyond the room, and the anchor lattice is shifted so a block can start exactly at the margin. A crop whose center cannot fit at all is `insufficient_space` (a squash at clearance 1 in a 24 in bed).
44. **Minimum group size.** Crop data gets an optional `minBlock` (corn: 3), the fewest plants along each side of a block; other crops normally grown in patches (`defaultPatch`) need at least `MIN_PATCH_PLANTS` (4) in a block, and solo crops (tomato) 1. It is a hard constraint on every block the solver places or resizes (an existing smaller patch keeps its shape and may still be moved). A crop whose target is below its smallest group is dropped before the search with the new reason `below_minimum_group`, and its share goes to the others; a demand's own `min` raises the target, so `min: 9` on corn asks for a whole block. Crops with a `min` are placed first, so they find their room before it is taken.
45. **Coverage term.** Each in-scope bed earns a concave reward (1 − (1 − r)², r = planted growing-room area over the fill ratio of the bed's area, fixed plants included), weighted by the bed's share of the scope's area and `COVERAGE_WEIGHT` (2) × `prefs.coverage` (default 1). A weight of 1 left a triangular bed 37% planted; 2 gives 56%. Beds fill evenly instead of the easy rectangle first, and an odd-shaped bed no longer stays nearly empty. The greedy bound includes it, so the branch-and-bound stays valid.
46. **Tidiness term.** Each crop in a bed beyond the first costs `MIX_WEIGHT` (0.15) × `prefs.tidiness` (default 0.5), fixed patches counted. On `north-row` this gives one crop per bed. The order is whatever the shade rule allows: lettuce is shade-tolerant, so corn may sit south of it, and a user who wants the tall crop north has to say so (a bed-level restriction on the demand).
47. **The search can add any crop**, not just ones below target (70% of "add" moves still go to under-target crops), so room left after the targets are met can be used. New blocks start at no less than the crop's smallest group.
48. **Default iterations 5000** (was 3000), in `solve` and the viewer. With the coverage term the greedy start is much better, so the search's median gain over it is smaller (0 to 0.18 in `--sweep`); the tests require a strict win only where there is room (`fill-bed-restricted`, `fill-min-max`, `adjust-locked`) and "never worse" everywhere. The slowest scenarios take well under a second at 5000.
49. **Viewer.** Hovering a plant names it (crop, spacing, "proposed"), a legend lists the crops and counts in each panel, and proposed plants sit on a light disc with a thin dashed ring that turns slowly (CSS, off under `prefers-reduced-motion`).
50. **Not done yet, from the same review:** whole-bed moves in the search ("make this bed all lettuce"), shape-specific fill patterns for curved and triangular beds, and block alignment or symmetry terms. Turning "remove the lettuce in the middle bed" into a command is the assistant layer's job (`removePatch` already exists); a spec cannot express a pure removal because it needs at least one demand.
51. **Adjust mode now fills gaps too.** With the coverage term and a roomier edge, an `adjust` spec that merely repeats what is there no longer emits nothing, because there is space left to plant. The 'no-op with stability 1' test therefore pins each crop's count with `min` and `max` and turns coverage off.
52. **The viewer ships in production.** It is experimental, there is nothing private in it (the fixtures are sample gardens and "Current garden" only reads the visitor's own browser storage), and it is much easier to try on the hosted site and in PR previews than to run locally. `App.tsx` still imports it lazily, so the solver and fixtures are a separate chunk that only `/_solver` fetches and the main bundle is unchanged. CI no longer greps for `solver-viewer` (it still guards the mock API). On GitHub Pages use the hash form, `#/_solver`, since the host 404s unknown paths.

### The crops card (planting view)

53. **A placeholder stands in for the solver for now.** The crops card (`src/app/planting/CropsCard.tsx`) was built first, on its own, so the interaction could be tried and tuned before it is joined to `solve`. `placeholderSuggest` (`src/solver/placeholderSuggest.ts`) implements the same `Suggester` interface the solver will: it takes the newest plants out of a crop, and puts new ones in the free spot furthest from everything else, with the same edge clearance as the solver. It does not rearrange, weigh crops against each other or consider shade, and "Try again" only shifts where it looks. The next step replaces it with an adapter around `solve` (a request's wants become demands, a bed becomes the scope), behind the same interface.
54. **The request rules are pure and in `core`.** `core/adjust.ts` holds what an arrow, a typed number and a cross do (more/fewer are soft directions that leave the count alone; typing sets an exact target; once a target exists the arrows step it; a target equal to the current count asks for nothing; 0 removes). The card only draws rows and reports presses.
55. **Left out on purpose: the optional note.** The design had a free-text note ("keep the basil near the tomatoes"). The solver cannot read free text, so a field that does nothing would mislead. It can come back if there is something deterministic to attach it to.

### Warnings on the garden

56. **A warning is tied to a plant, not to a corner of its patch.** Each warning links two patches. The garden now rings every plant of a warned patch in the warning color and puts the badge on the plant the warning is about (the one closest to the other patch), where it used to float at the top-right of the patch's box. Selecting or hovering either patch draws a dashed line to the closest plant of the other, with a label ("Too close", "Shade", "Keep apart"), and thickens the other patch's rings. The selection card says what the line is. Dismissed warnings draw nothing.
57. **Clicking one plant of a multi-plant selection selects just that plant.** Pressing a plant that is already one of several selected, then releasing without dragging, narrows to it (as it already did for a whole patch), so plants left selected after Ungroup, or boxed in, can be picked apart with a click; dragging still moves them all.
